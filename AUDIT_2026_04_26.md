## Playoff Modeling Engine Analysis

**Date:** April 26, 2026
**Scope:** NbaApi · BballTactics · NBASwiftTactics
**Trigger:** April 25, 2026 NBA Playoffs Round 1 games

## Executive Summary

Yesterday's (April 25) first-round playoff games were completely invisible to
the modeling engine. Three critical failures compound into a broken user
experience: the NbaApi hardcodes `Regular Season` across every query; the
BballTactics scraper runs on 5 hardcoded mock players and never touches the API;
and the Swift simulation deploys a 3-player bot team against a 5-player roster.
None of the playoff game data flows into the game. The audit below itemizes
every gap found across all three repos with severity ratings and implementation
notes.

## P0 — Breaks Core Functionality

### [NbaApi] P0-1: `season_type` hardcoded to `"Regular Season"` everywhere

**Files:** `server.py` — `_fetch_games`, `_fetch_last_night_analytics`,
`_fetch_team_analytics`

Every `LeagueGameFinder` call passes `season_type_nullable="Regular Season"`.
During the playoffs (mid-April through mid-June) the NBA Stats API returns zero
results for this filter, making every games endpoint return an empty list.

```python
# Current — breaks during playoffs
season_type_nullable="Regular Season",

# Fix: detect active season type from calendar
def _active_season_type() -> str:
    m = datetime.now().month
    return "Playoffs" if 4 <= m <= 6 else "Regular Season"

# Then expose as an optional query param with smart default
season_type_nullable=request.args.get("season_type", _active_season_type()),
```

This is a **same-day fix** — one helper + one parameter swap unblocks all
playoff data across `/api/games`, `/api/analytics/last-night`, and the team
dashboard recent-games list.

---

### [BballTactics] P0-2: `scraper.py` never calls the live NbaApi

**File:** `scraper.py:8–43`

`fetch_mock_data()` is the only data source — 5 players hardcoded to what
appears to be a 2023-24 snapshot. `build_engine_payload()` calls
`fetch_mock_data()` unconditionally; the real HTTP fetch is unimplemented.

```python
# Current
def fetch_mock_data(self):
    self.raw_players = [{"id": 1, "name": "Steph Curry", ...}]  # hardcoded

# Fix: call the live backend
def fetch_live_data(self, base_url: str = "http://localhost:5000"):
    import requests
    resp = requests.get(f"{base_url}/api/analytics/season")
    resp.raise_for_status()
    season_data = resp.json()["data"]
    self.raw_players = self._map_api_response(season_data)
```

Additionally, the stat-key mapping has a latent bug: `_calculate_z_scores` is
called with `"spd"` as the key but the nba_api payload field for speed is not
`"spd"`. A concrete field-name mapping table needs to be defined before wiring
the live data.

### [NBASwiftTactics] P0-3: Bot team is always 3 players vs. the player's 5

**File:** `GameManager.swift:spawnBotOpponents`

`spawnBotOpponents()` hard-codes exactly three bots (IDs 901–903) with fixed
stats (speed: 55–65, shooting: 40–50, defense: 50–60). The player's roster
fields up to five. Every game is an asymmetric 5v3; home win rates are inflated
by team-size advantage rather than real stat differentiation.

Fix: bot count must match `activeRoster.count`, and bot stats should be sampled
from the `engine_roster.json` distribution rather than fixed magic numbers.

## P1 — Significantly Hurts Model Accuracy

### [NbaApi] P1-1: `LeagueDashPlayerStats` has no playoff season-type filter

**File:** `server.py` — `_fetch_players`, `_fetch_last_night_analytics`

Both calls to `LeagueDashPlayerStats` omit a `season_type_detailed_defense`
parameter, so during the playoffs they return full regular-season cumulative
averages. A guard averaging 18 PPG in the regular season who is averaging 28 in
Round 1 is modeled at 18. Add
`season_type_detailed_defense=_active_season_type()` to both fetchers.

---

### [BballTactics] P1-2: Z-score normalization over wrong population

**File:** `scraper.py:_calculate_z_scores`

Z-scores computed over 5 players produce degenerate distributions — a single
outlier shifts every other player's stat by 20+ points. When real data is wired
in, the normalization must be computed over the **full league population first**
(~450 players), then individual z-scores are looked up from that distribution.
Computing z-scores over a filtered subset (e.g., one team's playoff roster) will
incorrectly compress the full 1–99 range into a narrow band.

---

### [NBASwiftTactics] P1-3: Shot probability ignores shot zone and type

**File:** `BasketballTactics/ShotProbability.swift`

`calculateShotProbability` applies a single exponential-decay curve regardless
of court zone. Real NBA eFG% by zone (league averages):

| Zone | eFG% |
|------|------|
| At rim (< 4 ft) | ~65% |
| Corner 3 (~22 ft) | ~58% |
| Mid-range (10–19 ft) | ~40% |
| Above-break 3 (~25 ft) | ~36% |

The current formula treats a Jokić mid-post turn-around and a wide-open corner
3 identically. Proposed fix: introduce a `ShotZone` enum and per-zone base
probability multipliers calibrated to league averages. The 200px threshold for
"3-pointer" also doesn't distinguish corner geometry.

---

### [NBASwiftTactics] P1-4: Free throws are not modeled

**File:** `BasketballTactics/Court.swift:attemptShot`

There is no foul-drawing mechanic. A contested shot simply reduces probability
with no chance of free throws. FT rate is a major playoff differentiator — a
high-foul-drawing star vs. a weak FT shooter in crunch time is unmodeled.

Fix: when a defender is within `< 5 ft` of the shooter at shot time, add a foul
probability (proportional to defender proximity × defense stat). On foul,
trigger `attemptFreeThrows(player:count:)` using the player's FT% from the
roster data.

---

### [BballTactics] P1-5: Salary cap hardcoded at $136M — stale for 2025-26

**Files:** `GameEconomy.swift:7`, `scraper.py:_determine_cost`

Both files hardcode `$136,000,000` — the 2023-24 cap figure. The 2025-26 cap is
approximately **$141M+**. Near-threshold players (those earning ~20% of cap) may
shift cost tiers incorrectly. Update to the current figure and add a comment
mandating a per-season sync between both files.

---

### [BballTactics] P1-6: Formation heatmap is an all-0.5 synthetic placeholder

**File:** `bots/balance/analyze.py:formation_heatmap`

```python
grid = np.full((5, 5), 0.5)  # placeholder — fill from real data if available
```

The chart is generated and saved with no real data — every cell reads 50% win
rate. This actively misleads balance interpretation. Either wire real position
outcomes from the simulation output into the grid, or gate the chart with a
visible `"Position data unavailable"` label until the data pipeline is live.

---

### [NBASwiftTactics] P1-7: `SynergyEngine` has no position-based synergies

**File:** `BasketballTactics/SynergyEngine.swift`

All four synergies check raw stat thresholds only (`heightInches`, `shooting`,
`defense`, `speed`). None of them use the `Position` enum that each
`PlayerEntity` already carries. Real NBA team-building is largely position-fit
driven. Proposed additions:

- **"Point-Center"** (PG + C with height ≥ 84") → +8 AST chance, +5 FG% near rim
- **"Wing Lock"** (2+ SF/PF with defense ≥ 75) → +10 opponent turnover rate
- **"Heliocentric"** (1 player USG% > 30 from real stats) → +15 shooting for
  that player, -5 for teammates

The `7 Seconds or Less` synergy also requires an average team speed > 85,
which is currently **unreachable** for bot opponents (max speed: 65). Bots will
never trigger the run-and-gun counter-narrative.

## P2 — Model Fidelity Improvements

### [NBASwiftTactics] P2-1: Stamina never depletes during simulation

`PlayerStats.stamina` is initialized to 100 and is never read or written
anywhere in `Court.swift`, `PlayerEntity.updatePhysicsTick`, or
`updateTransition`. Stamina depletion should progressively reduce speed and
shooting modifiers, reflecting playoff fatigue, heavy-minutes stars, and
back-to-back scheduling.

---

### [NBASwiftTactics] P2-2: No foul system — aggressive defense has zero cost

`Court.swift:updateSimulationStep` applies steal checks with no foul
accumulation. A defender can stay at 39.9px all game with zero penalty. Add a
foul counter per player; 6 fouls = fouled out (remove from team array). Playoff
foul trouble (a center picking up 3 fouls in the first quarter) is a primary
swing factor completely absent from the model.

---

### [NbaApi] P2-3: `CURRENT_SEASON` computed once at import time

**File:** `server.py:14–18`

A server started on September 30 serves the old season until restarted. Fix:
call `_current_nba_season()` inside each fetcher, or add per-request middleware
that checks and updates `CURRENT_SEASON` when the calendar has crossed October 1.

---

### [BballTactics] P2-4: Bot fallback is always `shooting=40` "Rookie AI"

**File:** `server.py:submit_and_fetch`

The no-opponent fallback bot stats are static across all 10 rounds. A player in
round 8 faces the same easy bot as round 1. Scale fallback bot difficulty by
`round_number`:

```python
base = 40
ramp = round_number * 3  # ~70 stats by round 10
bot_stats = {"shooting": base + ramp, "defense": base + ramp, "speed": base + ramp}
```

---

### [NBASwiftTactics] P2-5: No playoff bracket structure in `GameSeason.swift`

**File:** `BasketballTactics/GameSeason.swift`

`RoundType` has `standard5v5`, `playground3v3`, `horseMinigame`,
`draftLottery` — but no playoff bracket type. For gamification accuracy (and to
leverage the now-unblocked playoff data), add:

```swift
case playoffSeries(seed: Int, opponentTeamId: Int)
```

...with best-of-7 series tracking, home-court advantage speed buff (+5 speed for
the higher seed), and elimination stakes (series loss = run ends immediately
rather than flat 20-HP damage).

---

### [NbaApi] P2-6: No pagination and no playoff-eligibility filter on `/api/players`

**File:** `server.py:players`

Returns all ~450 players with no pagination. In the playoffs context, the shop
pool should be filterable to active-roster players only. Add
`?playoff_eligible=true` that cross-references current playoff team IDs, plus
`?page=` / `?per_page=` for bandwidth.

---

### [BballTactics] P2-7: `LakersStatsService` is siloed to one team

**File:** `BasketballTactics/LakersStatsService.swift`

Hardcodes `lakersTeamId = 14` and the class name/scope is Lakers-specific.
A generalized `TeamStatsService(teamId: Int)` conforming to a protocol would let
any playoff team's live stats feed the simulation — enabling matchup-specific
expected-outcome modeling (e.g., Thunder vs. Grizzlies Round 1 series).
